# Repository Guidelines

## Project Structure & Module Organization

- `src/` contains the TypeScript implementation. `protocol.ts` coordinates WDK operations; `route.ts`, `swap-data.ts`, and `fees.ts` handle routing, transaction validation, and fee policy; `index.ts` defines the public exports.
- `test/` contains Node test-runner suites named `*.test.ts`.
- `examples/` provides runnable discovery, quote, status, and swap flows. Keep example configuration documented in `.env.example`; never commit `examples/.env`.
- `dist/` is generated by TypeScript and is published with the package. Regenerate and commit it whenever public or runtime source changes.

## Build, Test, and Development Commands

- `npm install` installs the locked dependency set.
- `npm test` runs all tests through Node's built-in test runner and `tsx`.
- `npm run typecheck` checks both library and example TypeScript without emitting files.
- `npm run build` compiles `src/` into ESM JavaScript, declarations, and source maps under `dist/`.
- `npm run lint` currently aliases the type check.
- `npm pack --dry-run` verifies the package contents before release.
- `npm run example:quote` runs an example; equivalent scripts exist for `discover`, `status`, and `swap`.

## Coding Style & Naming Conventions

Use strict TypeScript, two-space indentation, single quotes, and no semicolons, matching the existing source. Prefer named types and small validation helpers at trust boundaries. Use `camelCase` for variables/functions, `PascalCase` for classes/types, and uppercase snake case for constants. File names are lowercase and hyphenated where needed. Preserve explicit `.js` extensions in source imports for NodeNext compatibility.

## Testing Guidelines

Use `node:test` with `node:assert/strict`. Place focused regression tests beside related coverage in `test/`, and name cases by observable behavior. Mock Butter HTTP responses and transaction adapters; unit tests must not require credentials or live-chain funds. Before submitting changes, run `npm test`, `npm run typecheck`, and `npm run build`.

## Security & Configuration

Treat Butter API responses as partially trusted. By project policy the `/swap` calldata is validated at a middle tier: always keep the router allowlist, the single-transaction rule on the built-in EVM path, the top-level intent checks (initiator, source token, source amount, empty permit, `feeData` vs route `feeConfig`), the `tx.value` check (`input + routerFee + bridgeFee`), the `maxNativeFee` cap, the same-chain destination checks, and the route-level fee caps — do not weaken these without security-focused tests. Source-denominated fee caps use the caller's `requestedAmountIn` as the denominator (never the untrusted `route.srcChain.totalAmountIn`), and ERC20 approval is always for the exact input amount (there is no unbounded/`max` option), so source-token exposure stays bounded. The `tx.value` check bounds native spend to `input + quoted routerFee + the bridge messaging fee Butter declares in the calldata`; that Butter-declared bridge fee is trusted and not otherwise bounded by the quote, so `maxNativeFee` (absolute cap on `routerFee + bridgeFee`) is the actual native-drain guard and cross-chain execution fails closed without it. Cross-chain destination routing (nested bridge payload: destination recipient, output token, minimum output) is intentionally trusted to Butter and NOT verified — this is a deliberate trust boundary, not full calldata intent validation; only the bridge's destination chain is checked, and source-token exposure stays bounded by the module's exact approval. EVM execution requires BOTH a full (send-capable) WDK account (per the WDK `swidge()` contract) AND `evm.walletClient` (its `account.address` validated against the WDK account) to carry calldata; the WDK `Transaction` type is only `{ to, value }`, so the account is used for the address and receipts, not for submitting swap calldata. ERC20 approval is always the exact input (an oversized allowance is reduced via `approve(0)`/`approve(amount)`), and an approval with no receipt source is refused rather than sent fire-and-forget. The calldata `feeData` must match the route's quoted `feeConfig` as a full `(feeType, referrer, rateOrNativeFee)` tuple: empty `feeData` is rejected when the route quoted a non-zero integrator fee, and a non-empty `feeData` requires the quoted tuple to be complete (fail closed on any missing field) and to match exactly, so `/swap` cannot inject an unchecked `feeType`/`referrer` by under-specifying the quote. Non-EVM adapter output is fully normalized and classified BEFORE any transaction is broadcast: every declared `type` must be a legal `SwidgeTransaction` role, a multi-transaction result must classify each entry (`{ transaction, type }`), and the set must resolve to exactly one `source` — any violation throws with nothing sent, so a failed classification can never leave a partially-broadcast operation that a retry could double-execute. A failure after one or more transactions are already out is unavoidable, so it is reported rather than discarded: both execution paths throw `ButterPartialExecutionError` carrying every broadcast hash (and register a broadcast `source` for status routing) instead of losing them with the stack frame. This covers a later send AND an approval that cannot be confirmed (revert, unknown receipt status, timeout) — that approval is already on the wire, so its hash must reach the caller; the original error is preserved as `cause`, and the swap is still never sent against it. A failure before anything is broadcast propagates unwrapped. Do not change this to swallow, re-order, or auto-retry the remaining legs. Approval-receipt confirmation and same-chain status share one classifier and fail closed (unknown/uninterpretable status is never treated as success). Same-chain status only trusts a receipt after attributing the source tx to an allowlisted Router (`swapAndCall`) — recorded ids are trusted, hints never bypass attribution — so an unrelated transaction is never reported as a completed swidge. Transaction/receipt lookups distinguish a genuine not-found (viem `TransactionNotFoundError`/`TransactionReceiptNotFoundError`, treated as absent) from infrastructure faults (RPC timeout, auth, rate-limit), which propagate to the caller instead of masquerading as "not found" and forcing a false `pending` or a silent cross-API fallback. That check must stay copy-independent (viem error `name` plus `BaseError` shape, not `instanceof` alone) because the host builds the wrapped client with its own copy of viem; keep the structural half so a real not-found is not misread as a fault, and keep the shape half so a fault cannot spoof a not-found by name. A cross-chain `/route` response must include a matching `dstChain` (a missing one is a same-chain path and is rejected). Keep API secrets server-side and out of logs, fixtures, and examples.

## Commit & Pull Request Guidelines

Follow the repository's Conventional Commit style, for example `fix: validate cross-chain native fees` or `feat: add runnable quote example`. Keep commits cohesive and include regenerated `dist/` output. Pull requests should explain behavior and security impact, link relevant issues or specifications, list verification commands, and document any public API or configuration changes. Screenshots are only needed for user-facing documentation changes.
