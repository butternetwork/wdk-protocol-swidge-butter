# Repository Guidelines

## Project Structure & Module Organization

- `src/` contains the TypeScript implementation. `protocol.ts` coordinates WDK operations; `route.ts`, `swap-data.ts`, and `fees.ts` handle routing, transaction validation, and fee policy; `index.ts` defines the public exports.
- `test/` contains Node test-runner suites named `*.test.ts`.
- `examples/` provides runnable discovery, quote, status, and swap flows. Keep example configuration documented in `.env.example`; never commit `examples/.env`.
- `dist/` is generated by TypeScript and is published with the package. Regenerate and commit it whenever public or runtime source changes.

## Build, Test, and Development Commands

- `npm install` installs the locked dependency set.
- `npm test` runs all tests through Node's built-in test runner and `tsx`.
- `npm run typecheck` checks both library and example TypeScript without emitting files.
- `npm run build` compiles `src/` into ESM JavaScript, declarations, and source maps under `dist/`.
- `npm run lint` currently aliases the type check.
- `npm pack --dry-run` verifies the package contents before release.
- `npm run example:quote` runs an example; equivalent scripts exist for `discover`, `status`, and `swap`.

## Coding Style & Naming Conventions

Use strict TypeScript, two-space indentation, single quotes, and no semicolons, matching the existing source. Prefer named types and small validation helpers at trust boundaries. Use `camelCase` for variables/functions, `PascalCase` for classes/types, and uppercase snake case for constants. File names are lowercase and hyphenated where needed. Preserve explicit `.js` extensions in source imports for NodeNext compatibility.

## Testing Guidelines

Use `node:test` with `node:assert/strict`. Place focused regression tests beside related coverage in `test/`, and name cases by observable behavior. Mock Butter HTTP responses and transaction adapters; unit tests must not require credentials or live-chain funds. Before submitting changes, run `npm test`, `npm run typecheck`, and `npm run build`.

## Security & Configuration

Treat Butter API responses as partially trusted. By project policy the `/swap` calldata is validated at a middle tier: always keep the router allowlist, the single-transaction rule on the built-in EVM path, the top-level intent checks (initiator, source token, source amount, empty permit, `feeData` vs route `feeConfig`), the `tx.value` bounds (a lower bound on the native input half; an upper bound on the fee half from `maxNativeFee` and from the quoted `routerFee + bridgeFee` plus a formatting-drift tolerance), the `maxNativeFee` cap, the same-chain destination checks, and the route-level fee caps — do not weaken these without security-focused tests. Source-denominated fee caps use the caller's `requestedAmountIn` as the denominator (never the untrusted `route.srcChain.totalAmountIn`), and ERC20 approval is always for the exact input amount (there is no unbounded/`max` option), so source-token exposure stays bounded. The `tx.value` check is deliberately two one-sided bounds rather than an exact `input + routerFee + bridgeFee` equality, because `/route` formats the router fee as a decimal string while `/swap` returns `tx.value` as a hex integer and a sub-wei artifact in that round-trip must not reject a good transaction: the native input half is a hard *lower* bound (anything less under-funds the swap), and the remaining fee half is bounded only from *above* — paying less than quoted cannot harm the user, since the router reverts if it is genuinely insufficient. The fee half's upper bounds are `maxNativeFee` (the security boundary) and the quoted `routerFee + bridgeFee` plus `NATIVE_FEE_DRIFT_BPS` (a consistency sanity check, not a security boundary). The Butter-declared bridge messaging fee is trusted and not otherwise bounded by the quote, so `maxNativeFee` (absolute cap on the whole fee half) is the actual native-drain guard, and cross-chain execution fails closed without it whenever the destination chain differs from the source chain — the requirement must not be conditioned on the calldata reporting a non-zero bridge fee, or a route that under-reports it opts out of the cap that bounds what `tx.value` actually spends. `maxNativeFee` may be overridden per call via `swidge(options)` — in either direction, since a single construction-time absolute cap cannot fit both a small and a large trade — and a per-call value satisfies the cross-chain requirement exactly as a configured one does; what must not change is that *some* cap is present cross-chain. Cross-VM destinations additionally require an explicit `options.recipient` on `swidge` (never on `quoteSwidge`, which must stay usable before a destination address is chosen): WDK's default of the source account address is only meaningful within one address family, and `NON_EVM_CHAIN_FAMILIES` in `constants.ts` is a best-effort table that must be extended whenever Butter adds a non-EVM chain — an unlisted chain is assumed EVM, which is the permissive direction. Cross-chain destination routing (nested bridge payload: destination recipient, output token, minimum output) is intentionally trusted to Butter and NOT verified — this is a deliberate trust boundary, not full calldata intent validation; only the bridge's destination chain is checked, and source-token exposure stays bounded by the module's exact approval. The single exception is an explicitly requested `options.refundAddress`: a caller who names a refund destination is asking for a guarantee, so the nested `refundAddress` is decoded and compared (raw 20 bytes for an EVM address, UTF-8 text otherwise) instead of asserted, and it fails closed with `ButterUnsupportedError` when the payload is empty or does not match the documented `(gasLimit, refundAddress, swapData)` layout — an unverifiable guarantee must never be reported as holding, and dropping `refundAddress` is the documented way back to Butter's default. Same-chain has no bridge payload, so `swapAndCall`'s `leftReceiver` carries that role and is compared against `refundAddress ?? sender`. Keep the asymmetry: an absent `refundAddress` must leave the nested payload undecoded, so the default path's trust boundary is unchanged. `refundAddress` is deliberately no longer required to equal the source sender — that constraint was never verified against the calldata, and it is meaningless across address families. EVM execution requires BOTH a full (send-capable) WDK account (per the WDK `swidge()` contract) AND `evm.walletClient` (its `account.address` validated against the WDK account) to carry calldata; the WDK `Transaction` type is only `{ to, value }`, so the account is used for the address and receipts, not for submitting swap calldata. ERC20 approval is always the exact input (an oversized allowance is reduced via `approve(0)`/`approve(amount)`), and an approval with no receipt source is refused rather than sent fire-and-forget. The calldata `feeData` must match the route's quoted `feeConfig` as a full `(feeType, referrer, rateOrNativeFee)` tuple: empty `feeData` is rejected when the route quoted a non-zero integrator fee, and a non-empty `feeData` requires the quoted tuple to be complete (fail closed on any missing field) and to match exactly, so `/swap` cannot inject an unchecked `feeType`/`referrer` by under-specifying the quote. Non-EVM adapter output is fully normalized and classified BEFORE any transaction is broadcast: every declared `type` must be a legal `SwidgeTransaction` role, a multi-transaction result must classify each entry (`{ transaction, type }`), and the set must resolve to exactly one `source` — any violation throws with nothing sent, so a failed classification can never leave a partially-broadcast operation that a retry could double-execute. A failure after one or more transactions are already out is unavoidable, so it is reported rather than discarded: both execution paths throw `ButterPartialExecutionError` carrying every broadcast hash (and register a broadcast `source` for status routing) instead of losing them with the stack frame. This covers a later send AND an approval that cannot be confirmed (revert, unknown receipt status, timeout) — that approval is already on the wire, so its hash must reach the caller; the original error is preserved as `cause`, and the swap is still never sent against it. The ordering is the invariant: a transaction is recorded the instant its send returns, BEFORE the gas fee it reported is validated, and the fee total and result assembly stay inside the guarded region — never validate-then-record, or a send that succeeded on-chain with a bad fee vanishes from the report. Sender-reported fees are checked as non-negative bigints and hashes as non-empty strings at runtime on both paths (host-supplied senders make the declared types hints, not guarantees; a `number` fee passes `< 0n` and would otherwise surface as a raw TypeError from the sum, and a `number` or empty hash would poison the operation id and the `toLowerCase()` status key). The hash is the one value validated BEFORE the transaction is recorded, because the hash is the record — a send that cannot be identified has nothing to report — and the last-resort reporter itself must never throw: registering a broadcast source for status routing is best-effort, handing the caller its hashes is not. A failure before anything is broadcast propagates unwrapped. Do not change this to swallow, re-order, or auto-retry the remaining legs. Approval-receipt confirmation and same-chain status share one classifier and fail closed (unknown/uninterpretable status is never treated as success). Same-chain status only trusts a receipt after attributing the source tx to an allowlisted Router (`swapAndCall`) — recorded ids are trusted, hints never bypass attribution — so an unrelated transaction is never reported as a completed swidge. Transaction/receipt lookups distinguish a genuine not-found (viem `TransactionNotFoundError`/`TransactionReceiptNotFoundError`, treated as absent) from infrastructure faults (RPC timeout, auth, rate-limit), which propagate to the caller instead of masquerading as "not found" and forcing a false `pending` or a silent cross-API fallback. That check must stay copy-independent (viem error `name` plus `BaseError` shape, not `instanceof` alone) because the host builds the wrapped client with its own copy of viem; keep the structural half so a real not-found is not misread as a fault, and keep the shape half so a fault cannot spoof a not-found by name. A cross-chain `/route` response must include a matching `dstChain` (a missing one is a same-chain path and is rejected). Keep API secrets server-side and out of logs, fixtures, and examples.

## Commit & Pull Request Guidelines

Follow the repository's Conventional Commit style, for example `fix: validate cross-chain native fees` or `feat: add runnable quote example`. Keep commits cohesive and include regenerated `dist/` output. Pull requests should explain behavior and security impact, link relevant issues or specifications, list verification commands, and document any public API or configuration changes. Screenshots are only needed for user-facing documentation changes.
