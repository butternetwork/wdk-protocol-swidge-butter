# Repository Guidelines

## Project Structure & Module Organization

- `src/` contains the TypeScript implementation. `protocol.ts` coordinates WDK operations; `route.ts`, `swap-data.ts`, and `fees.ts` handle routing, transaction validation, and fee policy; `index.ts` defines the public exports.
- `test/` contains Node test-runner suites named `*.test.ts`.
- `examples/` provides runnable discovery, quote, status, and swap flows. Keep example configuration documented in `.env.example`; never commit `examples/.env`.
- `dist/` is generated by TypeScript and is published with the package. Regenerate and commit it whenever public or runtime source changes.

## Build, Test, and Development Commands

- `npm install` installs the locked dependency set.
- `npm test` runs all tests through Node's built-in test runner and `tsx`.
- `npm run typecheck` checks both library and example TypeScript without emitting files.
- `npm run build` compiles `src/` into ESM JavaScript, declarations, and source maps under `dist/`.
- `npm run lint` currently aliases the type check.
- `npm pack --dry-run` verifies the package contents before release.
- `npm run example:quote` runs an example; equivalent scripts exist for `discover`, `status`, and `swap`.

## Coding Style & Naming Conventions

Use strict TypeScript, two-space indentation, single quotes, and no semicolons, matching the existing source. Prefer named types and small validation helpers at trust boundaries. Use `camelCase` for variables/functions, `PascalCase` for classes/types, and uppercase snake case for constants. File names are lowercase and hyphenated where needed. Preserve explicit `.js` extensions in source imports for NodeNext compatibility.

## Testing Guidelines

Use `node:test` with `node:assert/strict`. Place focused regression tests beside related coverage in `test/`, and name cases by observable behavior. Mock Butter HTTP responses and transaction adapters; unit tests must not require credentials or live-chain funds. Before submitting changes, run `npm test`, `npm run typecheck`, and `npm run build`.

## Security & Configuration

Treat Butter API responses as partially trusted. By project policy the `/swap` calldata is validated at a middle tier: always keep the router allowlist, the top-level intent checks (initiator, source token, source amount, empty permit, `feeData` vs route `feeConfig`), the `tx.value` cap (`input + routerFee + bridgeFee`, which guards native-balance drain), the same-chain destination checks, and the route-level fee caps — do not weaken these without security-focused tests. Cross-chain destination routing (nested bridge payload: destination receiver, output token, minimum output) is intentionally trusted to Butter and not re-verified; the bridge is still checked to target the quoted destination chain, and source-token exposure stays bounded by the module's exact approval. Keep API secrets server-side and out of logs, fixtures, and examples.

## Commit & Pull Request Guidelines

Follow the repository's Conventional Commit style, for example `fix: validate cross-chain native fees` or `feat: add runnable quote example`. Keep commits cohesive and include regenerated `dist/` output. Pull requests should explain behavior and security impact, link relevant issues or specifications, list verification commands, and document any public API or configuration changes. Screenshots are only needed for user-facing documentation changes.
