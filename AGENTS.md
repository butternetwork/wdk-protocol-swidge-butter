# Repository Guidelines

## Project Structure & Module Organization

- `src/` contains the TypeScript implementation. `protocol.ts` coordinates WDK operations; `route.ts`, `swap-data.ts`, and `fees.ts` handle routing, transaction validation, and fee policy; `index.ts` defines the public exports.
- `tests/` contains deterministic public-API suites named `*.test.ts`. `checks/` contains repository policy checks, and `scripts/e2e/` contains explicit live-network suites.
- `examples/` provides runnable discovery, quote, status, and swap flows. Keep example configuration documented in `.env.example`; never commit `examples/.env`.
- `dist/` is generated by TypeScript and is published with the package. Regenerate and commit it whenever public or runtime source changes.

## Build, Test, and Development Commands

- `npm install` installs the locked dependency set.
- `npm test` runs deterministic package tests through Node's built-in test runner and `tsx`.
- `npm run check:repo` runs documentation, release, example, and E2E-harness policy checks.
- `npm run typecheck` checks both library and example TypeScript without emitting files.
- `npm run build` compiles `src/` into ESM JavaScript, declarations, and source maps under `dist/`.
- `npm run lint` currently aliases the type check.
- `npm pack --dry-run` verifies the package contents before release.
- `npm run example:quote` runs an example; equivalent scripts exist for `discover`, `status`, and `swap`.

## Coding Style & Naming Conventions

Use strict TypeScript, two-space indentation, single quotes, and no semicolons, matching the existing source. Prefer named types and small validation helpers at trust boundaries. Use `camelCase` for variables/functions, `PascalCase` for classes/types, and uppercase snake case for constants. File names are lowercase and hyphenated where needed. Preserve explicit `.js` extensions in source imports for NodeNext compatibility.

## Testing Guidelines

Use `node:test` with `node:assert/strict`. Place focused public-API regression tests in `tests/`, and name cases by observable behavior. Mock Butter HTTP responses and transaction adapters; default tests must not require credentials or live-chain funds. Put repository policy checks in `checks/` and live-network scenarios in `scripts/e2e/`. Before submitting changes, run `npm test`, `npm run check:repo`, `npm run typecheck`, and `npm run build`.

## Security & Configuration

**Case-insensitivity is a property of EVM hex, not of identifiers — and normalization is per format space, not one operation.** `identifiers.ts` exposes two domains and they are not interchangeable. Token identifiers (`normalizeIdentifier` / `sameIdentifier`) lowercase **only** confirmed `0x`-hex. Transaction hashes (`normalizeTransactionHash` / `sameTransactionHash`) additionally accept bare 64-character hex, because Bitcoin and Tron txids carry no `0x` prefix and hex is case-insensitive regardless; length 64 is what keeps Base58 out, since a Solana signature is 87–88 characters and an address 32–44. Using one rule for both is wrong in both directions at once: the token rule rejected a BTC txid differing only in case, and the hash rule would normalize token identifiers it must leave alone. A third helper, `normalizeTokenKey`, exists solely so that building the `tokenDecimals` map and querying it use the **same** function — normalizing only the query left a checksummed configuration key unreachable from the equivalent lowercase request, and configured decimals were reported missing (masked whenever `/findToken` happened to resolve). Conflicting entries that normalize together are rejected at construction, since otherwise object key order would decide which decimals apply. Note `tokenDecimals` never applies to native tokens: `route.ts: decimalsFor` answers symbolic ids from `NATIVE_TOKEN_ADDRESSES` and `config.nativeTokenDecimals` first. The base rule below still governs what may be normalized at all — lowercase **only** a confirmed hex string — EIP-55 casing is a checksum over an address — and leaves everything else exactly as given. Solana mints and signatures and Tron addresses are Base58, where a character's case *is* part of the encoded value, so `AbCd…` and `abcd…` are different public keys. A blanket `toLowerCase()` merged them, and that had teeth in four places at once: a bridge fee in one mint was accepted as the caller's source token and handed the caller's own input as its fee denominator, passing a bps cap; a `/route` response satisfied the token-intent check with a differently cased token; two distinct mints collapsed into one discovery entry and shared a decimals cache slot; and two Solana signatures were treated as the same operation, reporting one transaction's status for another. Human-readable fields are the exception and stay plainly case-insensitive: token symbols, chain ids, chain type/name, status strings. `swap-data.ts`, `router-registry.ts`, and the router-deployment and signer checks in `protocol.ts` also stay as they are — those paths are EVM-only by construction, so their identifiers are always hex.

Treat Butter API responses as partially trusted. By project policy the `/swap` calldata is validated at a middle tier: always keep the router allowlist, the single-transaction rule on the built-in EVM path, the top-level intent checks (initiator, source token, source amount, empty permit, `feeData` vs route `feeConfig`), the `tx.value` bounds (a lower bound on the native input half; an upper bound on the fee half from `maxNativeFee` and from the quoted `routerFee + bridgeFee` plus a formatting-drift tolerance), the `maxNativeFee` cap, the same-chain destination checks, and the route-level fee caps — do not weaken these without security-focused tests. Source-denominated fee caps use the caller's `requestedAmountIn` as the denominator (never the untrusted `route.srcChain.totalAmountIn`), and ERC20 approval is always for the exact input amount (there is no unbounded/`max` option), so source-token exposure stays bounded. **`sourceTokenDecimals` is trusted because of where it comes from, not because of what it is called.** Two of its three sources are local — `config.tokenDecimals` and the chain's native default — but the third, `/findToken`, is a partially trusted remote response and must be validated before it is promoted: an entry counts only when its chain **and** its address match the request. Filtering on chain alone let a same-chain entry for a different token supply `decimals: 0`, which understated a source-denominated fee by orders of magnitude and slipped it under a bps cap, reaching the very bypass this value exists to close. Whenever a "trusted" input gains a new source, check its provenance rather than its name. A denominator in real base units also fixes the **scale**, so the matching numerator must be parsed with `FeeContext.sourceTokenDecimals` — the decimals this package resolved when building the `/route` request, carried on `CachedRoute.sourceDecimals` — and never with the route's own `srcChain.tokenIn.decimals`. `route.ts` verifies the source token's address but not its decimals, so a response claiming `decimals: 0` shrinks a 10 USDC fee from `10000000n` to `10n` and a thousand-basis-point charge reads as one hundredth of one. A route whose declared decimals disagree with the resolved value is refused outright (`trustedSourceDecimals`). This applies to every source-denominated numerator, including a bridge fee component whose token IS the source token; a cross-denominated component keeps its own declared decimals, because there numerator and denominator are both route-reported in the same token and the scale cancels. The actual Butter swap fee is authoritative from `swapFee`, which already includes the charge configured by `feeConfig`; fee mapping and `maxProtocolFeeBps` never derive a second amount from `feeConfig`. A configured protocol cap requires both `swapFee.nativeFee` and `swapFee.tokenFee`; absent values fail closed while explicit zeroes pass. `feeConfig` remains partially trusted calldata-validation metadata: non-empty `feeData` requires a complete tuple, a non-negative bigint `rateOrNativeFee`, and integer `feeType` in {0,1}, with typed `ButterTransactionValidationError` on malformed, unsupported, or mismatching values. Empty `feeData` is allowed when `rateOrNativeFee` is zero because no referrer fee is encoded; unused tuple fields are not validated on that path. `enforceLimit` still rejects negative numerators. This applies to a **source-denominated** fee whatever produces it: `fees.ts: bridgeFeeComponentRatio` must use `sourceDenominator` when a bridge fee component is charged in the source token, and may fall back to a route-reported amount only for a genuinely cross-denominated component. The two tests are deliberately opposite in strictness, and getting that backwards was itself a bypass. Recognizing the source token (`isSourceTokenComponent`) reduces to one rule: **a symbol can only ever confirm a symbolic identifier.** A declared address decides on its own; the symbol is consulted only when the component carries no address *and* `sourceToken` is itself symbolic (`SYMBOLIC_NATIVE_TOKEN_IDS` — `native`/`btc`/`trx`/`sol`), which is the genuine shape on a non-EVM source. When `sourceToken` is an address of any kind, no symbol can establish a match and an address-less component is unidentifiable, hence refused. Use the closed set, not a `0x` shape test: that would classify a Solana mint or Tron base58 address as symbolic and reopen the hole one chain over. Every clause closes a bypass found in a separate review round, and they pull in different directions — requiring an address outright pushed a symbol-only source component into the route-controlled denominator; letting a symbol beat an address divided a foreign token's fee by the caller's source amount; an ungated symbol fallback let any component claim that amount by naming the source address in its `symbol`. Because this rule has failed in three directions, preserve its public outcomes in `tests/fees.test.ts` and the protocol execution suite whenever the component-matching logic changes. A trusted denominator is not automatically a meaningful one: `requestedAmountIn` is the right divisor only for a fee actually charged in the source token. Matching a component to a route **leg** (`sameTokenAddress`) requires an address on both sides, because a symbol is not an identifier: the same ticker exists on many chains, so a symbol match can pick an amount that is not in the fee's currency. A cross-denominated component naming no address, and a component with no same-token denominator, both throw `ButterFeeValuationError`. Routing a source-token fee through those candidates reopens the bypass in full: inflate `srcChain.totalAmountIn` and any ratio can be pushed under a bps cap. `bridgeFee` is priced per component (`in`, `out`, `affiliate`, each with its own token and each with a `role` that decides which route leg may serve as its denominator — `in` and `out` are usually the same token, so a shared candidate order measured the outbound fee against the inbound amount). The top-level `bridgeFee.amount` summary is **never priced** — not as a component, not reconstructed as `amount - affiliate`, and not even compared against the components' sum. It is one figure with one token for a fee that can span three tokens, so it is both unattributable and forgeable: a partially trusted response can omit the real components and supply a small, conveniently-denominated summary that satisfies any bps cap. Amounts in different tokens are also not addable, so any arithmetic mixing the components is meaningless by construction. The summary serves only as a **detector**: when no component is present, `mapRouteFees` warns `bridge-fee-components-missing` and omits the fee, and a configured protocol cap throws `ButterFeeValuationError`. It is equally unfit as *evidence*: the cross-chain "did this route report a bridge fee" test counts only `in`/`out`/`affiliate` amounts (`hasBridgeFeeComponents`) — an explicit component `"0"` is a real answer and passes, but a bare `{ amount: "0" }` does not, or a response satisfies `maxProtocolFeeBps: 0` by reporting a summary it was never willing to stand behind. `affiliate.amount` must be one of the counted fields, or an affiliate-only route is rejected as if it reported nothing. The trusted-decimals rule applies to **quoting as well as capping** (`componentDecimals`, and `swapFee.tokenFee` in `mapRouteFees`): a quote needs no cap configured for a caller to read an understated number and act on it. The affiliate component IS aggregated into `maxProtocolFeeBps` even though `fees[]` types it `affiliate`: WDK has no affiliate cap, and an unset `config.affiliate` means Butter takes the cut with its own wallet, so this is the only bound available to the user. Keep that deviation — and keep it out of the fee *type*, which stays `affiliate`. The `swapFee` object is the authoritative actual Butter swap fee and already includes any charge configured by `feeConfig`; fee mapping and protocol caps use `swapFee` only, while `feeConfig` is retained solely for calldata consistency validation. Fee caps also distinguish **absent** metadata from an explicit zero — an unreported `gasFee.amount` (network cap) or an unreported `bridgeFee.amount` on a cross-chain route (protocol cap) throws `ButterFeeValuationError`, because scoring a missing fee as free would let Butter pass any cap by omitting the field, while `'0'` is a real answer that passes. Exact-out is currently rejected before any network request (`ButterExactOutUnsupportedError`): Butter documents `type: exactOut`, but the default production endpoint answers `errno 2000` and the docs define `amount` only as "amount of source token" with no exactOut variant, so the denomination to send is unspecified — `npm run example:probe-exact-out` re-checks both. A future exact-out implementation requires a fresh input-bound design and security review; the exact-in calldata and fee validators intentionally contain no dormant exact-out branch. The `tx.value` check is deliberately two one-sided bounds rather than an exact `input + routerFee + bridgeFee` equality, because `/route` formats the router fee as a decimal string while `/swap` returns `tx.value` as a hex integer and a sub-wei artifact in that round-trip must not reject a good transaction: the native input half is a hard *lower* bound (anything less under-funds the swap), and the remaining fee half is bounded only from *above* — paying less than quoted cannot harm the user, since the router reverts if it is genuinely insufficient. The fee half's upper bounds are `maxNativeFee` (the security boundary) and the quoted `routerFee + bridgeFee` plus `NATIVE_FEE_DRIFT_BPS` (a consistency sanity check, not a security boundary). The Butter-declared bridge messaging fee is trusted and not otherwise bounded by the quote, so `maxNativeFee` (absolute cap on the whole fee half) is the actual native-drain guard, and cross-chain execution fails closed without it whenever the destination chain differs from the source chain — the requirement must not be conditioned on the calldata reporting a non-zero bridge fee, or a route that under-reports it opts out of the cap that bounds what `tx.value` actually spends. `maxNativeFee` may be overridden per call via `swidge(options)` — in either direction, since a single construction-time absolute cap cannot fit both a small and a large trade — and a per-call value satisfies the cross-chain requirement exactly as a configured one does; what must not change is that *some* cap is present cross-chain. Cross-VM destinations additionally require an explicit `options.recipient` on `swidge` (never on `quoteSwidge`, which must stay usable before a destination address is chosen): WDK's default of the source account address is only meaningful within one address family, and the address-family tables in `constants.ts` (`NON_EVM_CHAIN_FAMILIES`, `KNOWN_EVM_CHAIN_IDS`) are best-effort and must be extended whenever Butter adds a chain. A chain in neither table resolves to `'unknown'`, **not** to `'evm'`, and an unknown family on either side requires an explicit recipient exactly as a differing one does — two unknowns must never be treated as matching. Butter adds chains without this package being republished, so assuming EVM would silently reuse a `0x` sender as the receiver on a newly added non-EVM chain. `config.evmChainIds` lets an integrator accept a not-yet-listed EVM chain without patching this table. Cross-chain destination routing (nested bridge payload: destination recipient, output token, minimum output) is intentionally trusted to Butter and NOT verified — this is a deliberate trust boundary, not full calldata intent validation; only the bridge's destination chain is checked, and source-token exposure stays bounded by the module's exact approval. The single exception is an explicitly requested `options.refundAddress`: a caller who names a refund destination is asking for a guarantee, so the nested `refundAddress` is decoded and compared (raw 20 bytes for an EVM address, UTF-8 text otherwise) instead of asserted, and it fails closed with `ButterUnsupportedError` when the payload is empty or does not match the documented `(gasLimit, refundAddress, swapData)` layout — an unverifiable guarantee must never be reported as holding, and dropping `refundAddress` is the documented way back to Butter's default. Same-chain has no bridge payload, so `swapAndCall`'s `leftReceiver` carries that role and is compared against `refundAddress ?? sender`. Keep the asymmetry: an absent `refundAddress` must leave the nested payload undecoded, so the default path's trust boundary is unchanged. `refundAddress` is deliberately no longer required to equal the source sender — that constraint was never verified against the calldata, and it is meaningless across address families. EVM execution requires BOTH a full (send-capable) WDK account (per the WDK `swidge()` contract) AND `evm.walletClient` (its `account.address` validated against the WDK account) to carry calldata; the WDK `Transaction` type is only `{ to, value }`, so the account is used for the address and receipts, not for submitting swap calldata. ERC20 approval is always the exact input (an oversized allowance is reduced via `approve(0)`/`approve(amount)`), and an approval with no receipt source is refused rather than sent fire-and-forget. The calldata `feeData` must match the route's quoted `feeConfig` as a full `(feeType, referrer, rateOrNativeFee)` tuple: empty `feeData` is rejected when the route quoted a non-zero referrer fee, and a non-empty `feeData` requires the quoted tuple to be complete (fail closed on any missing field) and to match exactly, so `/swap` cannot inject an unchecked `feeType`/`referrer` by under-specifying the quote. Non-EVM adapter output is fully normalized and classified BEFORE any transaction is broadcast: every declared `type` must be a legal `SwidgeTransaction` role, a multi-transaction result must classify each entry (`{ transaction, type }`), and the set must resolve to exactly one `source` — any violation throws with nothing sent, so a failed classification can never leave a partially-broadcast operation that a retry could double-execute. A failure after one or more transactions are already out is unavoidable, so it is reported rather than discarded: both execution paths throw `ButterPartialExecutionError` carrying every broadcast hash (and register a broadcast `source` for status routing) instead of losing them with the stack frame. This covers a later send AND an approval that cannot be confirmed (revert, unknown receipt status, timeout) — that approval is already on the wire, so its hash must reach the caller; the original error is preserved as `cause`, and the swap is still never sent against it. The ordering is the invariant: a transaction is recorded the instant its send returns, BEFORE the gas fee it reported is validated, and the fee total and result assembly stay inside the guarded region — never validate-then-record, or a send that succeeded on-chain with a bad fee vanishes from the report. Sender-reported fees are checked as non-negative bigints and hashes as non-empty strings at runtime on both paths (host-supplied senders make the declared types hints, not guarantees; a `number` fee passes `< 0n` and would otherwise surface as a raw TypeError from the sum, and a `number` or empty hash would poison the operation id and the `toLowerCase()` status key). The hash is the one value validated BEFORE the transaction is recorded, because the hash is the record — a send that cannot be identified has nothing to report — and the last-resort reporter itself must never throw: registering a broadcast source for status routing is best-effort, handing the caller its hashes is not. A failure before anything is broadcast propagates unwrapped. Do not change this to swallow, re-order, or auto-retry the remaining legs. Approval-receipt confirmation and same-chain status share one classifier and fail closed (unknown/uninterpretable status is never treated as success). Same-chain status only trusts a receipt after attributing the source tx to an allowlisted Router (`swapAndCall`) — recorded ids are trusted, hints never bypass attribution — so an unrelated transaction is never reported as a completed swidge. Transaction/receipt lookups distinguish a genuine not-found (viem `TransactionNotFoundError`/`TransactionReceiptNotFoundError`, treated as absent) from infrastructure faults (RPC timeout, auth, rate-limit), which propagate to the caller instead of masquerading as "not found" and forcing a false `pending` or a silent cross-API fallback. That check must stay copy-independent (viem error `name` plus `BaseError` shape, not `instanceof` alone) because the host builds the wrapped client with its own copy of viem; keep the structural half so a real not-found is not misread as a fault, and keep the shape half so a fault cannot spoof a not-found by name. A cross-chain `/route` response must include a matching `dstChain` (a missing one is a same-chain path and is rejected). Token pagination answers two questions with **two separate mechanisms**, and conflating them has broken it in both directions. How far through the list are we: `count` counts raw rows, so `consumed` advances by raw page size — counting distinct records instead made a page containing an in-page duplicate fall short of `count` and abort a legitimate response. Is the server actually paginating: a record already returned on an *earlier* page is an error, since the walk is looping or the list shifted and `consumed` would reach `count` with the tail never fetched. Repeats within one page are fine; repeats across pages are not. The advertised `count` is also pinned to the first page, a later page changing it being an error. Both other readings have been wrong in production — counting surviving tokens stalls the walk forever once one is filtered, and counting page size alone lets a server replaying page 1 reach `count` and return a silent fraction of the list. Keep API secrets server-side and out of logs, fixtures, and examples.

## Commit & Pull Request Guidelines

Follow the repository's Conventional Commit style, for example `fix: validate cross-chain native fees` or `feat: add runnable quote example`. Keep commits cohesive and include regenerated `dist/` output. Pull requests should explain behavior and security impact, link relevant issues or specifications, list verification commands, and document any public API or configuration changes. Screenshots are only needed for user-facing documentation changes.
